## v2.3.0 — 安装时自动部署代理、通知铃铛与界面精简（2026-10-25）

### Added

- **启动时自动检查更新 + 通知铃铛**（主窗口右上角，位于运行控制栏最右侧）：
  - 每次启动在后台查一次（延迟 6 秒，不拖慢启动）。设置里可选「不检查更新 / 有更新时通知我 /
    有更新时自动下载」，默认「有更新时通知我」。
  - 有更新时在铃铛里挂一条通知：未读时有红点、铃铛每 2 秒轻摇一次，读完立刻停。
    通知与已读状态存在程序目录的 `notifications.json`（最多 50 条），关掉程序再开还在；
    同标题不重复添加，所以每次启动都查也不会攒出一串复读。
  - 选「自动下载」时后台把安装包下到程序目录的 `updates\`，下完弹框问「现在安装吗」——
    不静默安装：安装程序会先关掉 Yomori，跑到一半的任务会断。
  - 检查更新与下载都支持「系统代理 / 自定义代理（形如 `http://127.0.0.1:7890`）/ 不使用代理」，
    设置项在「设置 → 关于」。手动点「检查更新」也走同一套代理设置。
- **安装时自动部署会话代理**：安装程序在文件铺完后调用 `Yomori.exe --deploy-agent`，
  把随包的代理载荷部署到 `%ProgramData%\Yomori\agent` 并登记「所有用户」的登录自启项。
  装完即可连接目标账户，不必先想起来去点一次「部署会话代理」。
  - 复用界面部署按钮的同一套逻辑（含副本占用时退到 `agent_b` 的处理），只是去掉交互：
    不弹窗、不参与单实例，退出码就是结论（0 已部署 / 1 失败 / 2 代理正在执行任务 / 3 缺管理员权限）。
  - **幂等**：载荷内容与已部署副本一致就跳过整套搬运，覆盖安装不会白搬约 73MB。
  - **已有自启项不重写**：其中的 `--bridge:` 是用户通道配置里定的，安装程序不替用户改。
    只有自启项不存在时才新建，桥目录取自 `config.json` 里唯一的那一个 `bridge_path`。
  - **不打断正在执行的任务**：部署前扫全部桥的状态，任一桥有活跃任务就整轮跳过
    （安装结束后手动点一次部署即可补上）。
  - 失败不阻断安装；结论与原因写在安装目录的 `logs\agent_deploy.log`。

### Changed

- **通道页布局改为左右分栏**：内嵌画面在左侧，运行信息（运行事件 / 实时日志）竖排到右侧；
  两栏之间的分隔条**可拖动**改比例，拖完的宽度记进 `config.json`（`window.channel_events_width`），
  下次进页面沿用。运行信息栏可整栏收起（收起后画面多占约 264px）。
  此前运行信息在画面下方且写死 174px 高，窗口稍矮就把画面压成一条横带，
  运行信息自己也溢出到窗口外（1080p 实测看不全）。
  右侧栏只有 260–420px，顺手把「清空当前显示」缩为「清空」、日志跟随状态单独占一行。
- **通道页去掉「任务：－ / 进度 / 心跳」那条横条**：画面让位，进度与心跳改在
  主窗口右侧执行状态栏与多画面页查看。
- **通道管理页删掉「本轮运行状态」与「画面在会话通道里」两块卡**：前者是各通道进度的
  重复展示（主窗口右侧「执行状态」栏已有），后者只是两句话加两个跳转按钮 ——
  左侧菜单本来就能直接去。本页回归"只做配置与预检"。
  随之去掉那条红色「会话代理已失联」提示条：失联仍会以状态文本呈现（含最后心跳时刻），
  运行事件里也照旧记录。
- **「运行日志」页默认也隐藏 `[memory]` 内存探针行**：此前只挡 `[embed]`，内存采样
  （`[memory] private_mib=… working_set_mib=…`，以及内嵌画面那份 `live_sessions=…`）
  照样每分钟刷进来。现在两类诊断行都只在「设置 → 开发者」里打开开发者模式后显示，
  日志文件里始终完整保留；页面上那句提示也改成同时点名两类标签。
- **卸载时清理代理副本与自启项**：`%ProgramData%\Yomori\agent`、`agent_b` 与公共启动目录里的
  快捷方式都随卸载删除。指令桥目录 `%ProgramData%\Yomori\rdp\` 保留 —— 那是任务状态与统计，
  属于用户数据。
- **仓库地址统一为新名 `AITNR/Yomori`**：检查更新（GitHub Releases 接口）、设置页「关于」里的
  GitHub 按钮、安装包的「支持网址」原先都写着改名前的 `Anigame-script-manager`，
  每次都多经一次 301 重定向。旧地址仍可访问，但新装的包与之后的检查更新都直连新地址。

### Fixed

- **设置页「外部脚本日志」看不到真实日志、也清不掉**：任务跑在目标账户会话里时，日志是**代理**
  写的，落在 `%ProgramData%\Yomori\agent\external_logs`；而「查看占用 / 清理超出的 / 打开日志目录」
  只认主控端安装目录下的 `external_logs`。表现是界面永远「暂无文件」、清理永远删不到东西、
  打开目录打开的是个空文件夹，而那份日志其实一直在涨（实测一台机器上积到 283MB 未被清理）。
  现在占用、清理与打开目录都同时覆盖两处（本机执行 / 目标账户会话），占用明细也标注来源；
  「打开日志目录」优先打开真正在写日志的那一处。
- **通道页「该通道任务全部结束后的会话处理」下拉框空白**：模型默认值本来是「保持连接
  （方便随时切过去看结果）」，但该下拉框用 `x:Bind` 绑了 `VM.SelectedChannel.SessionFinish`
  （两级路径 + `SelectedValue`）。首次求值时选中通道还是空的、选项列表也还没填，
  那一次赋值被 ComboBox 丢弃，之后填了选项也不会重新匹配 —— 下拉框就一直没有选中项。
  改成选项列表在构造函数里给、选中值随「选中通道」在代码里同步，改值后显式写回通道并落盘。
- **「测试版」更新渠道给的是正式版**：测试版通道原先在**全部**发布里按版本号取最大，
  而正式版（`v2.2.1`）与 CI 滚动构建（`2.0.0-dev.105`）根本不在同一套编号里，正式版永远赢 ——
  用户把渠道切到「测试版」，检查结果却是「发现新版本 2.2.1（测试版）」。
  现在**渠道决定候选集**（测试版只看预发布）、**版本号只在同类里排序**；
  该通道确实没有构建时如实说明"测试版通道暂无构建"，不再退而求其次拿正式版凑数。
  装了正式版的人切到测试版时，看到的也是"编号体系不同、别按大小理解"的说明，
  而不是原来那句容易让人以为"远端回退了"的文案。

## v2.2.1 — 界面精简与渲染后端下拉框修复（2026-10-24）

### Changed

- **通道预检区去掉「开启远程桌面」按钮**：这一步改由用户在目标机器的系统设置里完成
  （设置 → 系统 → 远程桌面）。预检仍会检查该项，未开启时在检查结果里提示，连接前也会拦一次。
- **内嵌相关文案去掉「实验性」标注**：连接方式选项改为「内嵌到Yomori窗口」；
  勾选项改为「GFX 全帧管线（撕裂根治，需重连生效）」。

### Fixed

- **「内嵌画面渲染后端」下拉框显示空白**：`x:Bind` 先给 ComboBox 赋 `SelectedValue`、
  再填 `ItemsSource`，列表为空时那次赋值被丢弃，之后填了选项也不会重新匹配，于是永远没有选中项。
  现在把数据源与选中值都放在页面构造函数里先摆好（早于 x:Bind 求值），
  默认显示「D3D11 硬件加速（默认，失败自动回退软渲染）」。配置值本身一直是 `auto`，只是没显示出来。

## v2.2.0 — 更名为 Yomori，界面改版（2026-10-24）

### Changed

- **项目更名为 Yomori**（原「雪乃酱 / YukinoChan」）。新名称不再沿用受版权保护的角色名，
  也不把产品绑定到某一款游戏。
  - 可执行文件 `Yomori.exe`、程序集与命名空间 `Yomori.*`、解决方案 `Yomori.sln`；
  - 运行数据目录 `%ProgramData%\Yomori\`（原 `%ProgramData%\YukinoChan\`）；
  - AppUserModelID `com.aitnr.yomori.app`、单实例名、Toast 显示名同步更换。
  - 原生桥接库仍名 `ycn_rdp.dll`，导出函数前缀 `ycn_` 保留 —— 它是 C ABI，
    重命名需要重新编译 FreeRDP 桥接层，与产品名无关。
- **移除看板娘**：右侧面板、状态机、气泡文案与 `assets/mascot/` 素材一并删除，
  窗口恢复单列布局。`config.json` 不再写入 `window.mascot_panel`
  （旧配置里的该键会被忽略，不需要手工清理）。运行状态仍由主页状态卡与通道概览呈现。
- **更换应用图标**：`assets/icon.ico` 换为新 logo（16–256 共 9 档尺寸），
  另存 `assets/logo.png` 供标题栏与文档使用。两者背景均为**透明**——
  原先是白底圆角图，深色标题栏与任务栏上会露出一块白方框。
- **会话代理改为独立工程**（`src/Yomori.Agent`）：代理不再复用主控端可执行文件，
  单独发布一份不引用 WinUI / WindowsAppSDK 的纯后台程序，随包放在安装目录的 `agent\` 下。
  - 部署到 `%ProgramData%\Yomori\agent` 的体积由 **228MB 降到约 73MB**，
    进程私有内存约 9MB；界面栈、Windows App SDK、ONNX/DirectML 等代理用不到的组件不再分发。
  - 升级后首次部署会**整目录重建**旧副本（旧的那份是主控端整目录复制品，
    覆盖式更新会把其中约 150MB 的界面栈永久留在磁盘上）。
  - 安装目录缺少 `agent\` 时（开发期直接 `dotnet build`）仍回退到旧的整目录复制行为。
- **主窗口新增右侧执行状态栏**（可收起，宽度 264 / 44px，收起状态写入 `window.sidebar_collapsed`）。
  集中显示本轮状态（运行中 / 有异常 / 空闲）、总进度与已耗时、当前任务，以及按通道分列的执行项目列表；
  每行显示该通道自己的进度条，在跑的一行前面亮蓝点。展开与收起带过渡动画（淡出 → 变宽 → 淡入），
  宽度动画按布局属性处理，必须开启 `EnableDependentAnimation` 才会生效。
  状态栏与内容交界的一侧改为圆角，规则与左侧导航栏一致。
- **执行状态栏新增「异常原因」区块**：显示首条原因与剩余条数，悬浮可查看全部。
  代理侧将执行结果按三种情况分别表述 —— 真实异常、已停止（本轮未跑完）、全部任务已完成。
- **首页改版**：
  - 版式改为通栏横幅 + 下方卡片区，横幅吃满中间剩余高度（`MinHeight` 160 兜底）；
  - 横幅图片不再固定在包内单张默认图，改为每次进入首页（含启动）从 `assets/home_banners/` 随机抽取。
    图库认 png / jpg / jpeg / bmp / gif / webp，图库中有多张时不会连续抽到同一张，原
    `assets/home_banner.jpg` 已删除。右键菜单为「换一张」「更换图片…」「恢复随机展示」；
    `config.json` 的 `home_banner` 语义变为「钉死某一张」，清空即回到随机。
  - 快捷入口压成一行四卡（只留图标与标题），新增「通道管理」入口；
  - 左侧菜单「总览」更名为「首页」，页面类与导航 tag（`home`）不变。
- **任务执行页**：
  - 每个通道行右侧新增执行开关，写回通道配置的 `enabled`（与「通道管理」页同一份数据，两处同步），
    切换后就地刷新该行，不重建通道列表；
  - 任务行序号前新增抓手，拖动排序整行跟随指针、其余行让位，松手时才写入顺序；
    顺序只重排本组已占用的值，多组之间不冲突。让位过程为 120ms 补间。
- **安装包体积**：打包出口裁掉 WinUI 内置控件的非中文语言目录（保留 zh-CN / zh-TW / en-us）
  与全程序零引用的 AI / ML / Widgets 载荷（onnxruntime、DirectML 等），
  安装目录从 452 条目 / 301MB 降至 193 条目 / 114MB（不含 `agent\`）。
- **界面文案**：移除「二游脚本助手」副标题，窗口标题与横幅只保留 Yomori；「关于」页文案同步改写；
  标题栏左上角徽标由手写的「雪」字方块改为应用 logo。

### Fixed

- **全屏模式下键盘按键收不到抬起事件**（粘键、字符连续重复、后续按键变组合键、Shift/Ctrl 卡住）。
  全屏键盘走 `WH_KEYBOARD_LL` 钩子，而钩子回调中 `KBDLLHOOKSTRUCT` 的字段偏移原先按每字段 8 字节手算，
  实际布局为 0/4/8/12/16、结构体大小 24：扫描码读到的是 `flags`，抬起时 `LLKHF_UP`（0x80）被当作扫描码
  发往远端，远端无法识别。改为用 `Marshal.PtrToStructure` 解析结构体，并以行为断言锁定结构与偏移。
  同时修正同族两处：钩子仅在当前前台窗口正是全屏窗口时接管键盘，失焦、重新聚焦与退出全屏时各补发一轮
  修饰键抬起。
- **任务页点「浏览」选择脚本会导致进程退出**（桌面残留无响应窗口，单实例互斥量被占，重开无法启动）。
  根因是文件选择器返回的 awaitable 不捕获同步上下文，续体落在线程池上，随后在非 UI 线程写绑定属性触发
  `COMException 0x8001010E`，而该事件处理器为 `async void`，异常无人接管。收口在对话框帮助类内部：
  打开与保存对话框的返回值一律在 UI 线程交付。
- **切换页面返回后内嵌画面为空白**。原生帧回调仅在远端画面确有变化时触发，远端桌面静止时没有新帧，
  而渲染器与首次呈现都挂在「新帧到达」上，于是切页回来后永远等不到第一帧。现在挂载后会主动补抓一次
  原生缓存的最后一帧（重试上限约 10 秒），渲染器就地创建，无需等待下一次帧到达。
- **点击左侧「会话通道」父项会跳转到多画面页**，与点击子项「多画面」表现相同。父项改为不随点击选中，
  并在选中变更处理中兜底：若父项被设为当前选中项，不导航并把选中态拉回当前页面。
- **执行状态把用户主动执行的「紧急停止」报为「已完成（有异常）」**，且日志中只有收尾语、没有具体原因
  （现场为按下「紧急停止全部」后进度停在 3/4）。代理侧改为按真实异常 / 已停止 / 全部完成三种情况分别表述；
  主控端对旧代理副本亦做兜底 —— 本轮已被用户停止时，上报的异常不再计入。
  汇总明细不再用收尾语冒充原因，一条明细都没有时明确提示查看运行日志。
- **图标在深色标题栏与任务栏上呈白底方框**。`logo.png` 与 `icon.ico` 原先只有四角透明、中间整块不透明白，
  现改为完全透明背景（逐档重出 16–256 共 9 档），并以像素级断言防止回归。
- **自旧版升级时安装目录仍被旧路径覆盖**，装回 `C:\Program Files\YukinoChan`。Inno Setup 的
  `UsePreviousAppDir` 默认取旧版登记的 `InstallLocation`，会覆盖 `DefaultDirName`。现显式关闭该项，
  并在安装收尾删除旧目录空壳（仅空目录）。已固定到任务栏或开始屏幕的旧快捷方式仍指向旧路径，需重新固定。

### 升级注意

- **升级后必须重新部署会话代理，并注销目标账户后重连一次。**
  代理副本位于 `%ProgramData%` 下，目录名随产品改名而变；
  旧版部署在 `%ProgramData%\YukinoChan\agent` 的那份副本不会被新程序读取。
  旧目录可以保留作为回退，不会影响新版本运行。
- 安装版安装目录由 `C:\Program Files\YukinoChan` 变为 `C:\Program Files\Yomori`。
  安装包 AppId 未变，**直接运行新安装包即可**：它会先静默卸载旧版，再把文件铺到新目录，
  不需要先进「应用和功能」手动卸载。旧目录为空时会一并删除。
  已固定到任务栏或开始屏幕的旧快捷方式仍指向旧路径，需取消固定后重新固定。

## v2.1.1 — 建连前下发的静音意图不再丢失（2026-10-22）

### Fixed

- **内嵌画面的静音按钮显示「已静音」，实际仍有声音；必须关一次再开一次才真的静音。**
  根因是静音意图在**会话建立之前**下发、被原生侧拒绝后**没有任何一处重发**：
  `ycn_rdp_set_muted` 要求会话处于 `RUNNING` 状态，其余状态直接返回 `YCN_ERR_NOT_CONNECTED`
  且不改静音标志。而界面侧的三次下发 —— 发起连接**之前**、画面挂载时、以及建连过程中点按钮 ——
  全都可能落在 `RUNNING` 之前，于是这次调用被丢掉；图标读的是界面自己记住的「本通道已静音」，
  与原生真实标志脱钩，表现为图标说静音、声音照放。用户手动关一次（会话已 `RUNNING`，成功写 0）
  再开一次（成功写 1），两边才重新对齐。

  现在客户端把「最新静音意图」记在会话封装里，在 `Connected` 回调触发时补发一次：
  补发交线程池执行（不在 FreeRDP 的 `PostConnect` 里就地抢锁调设备 `SetVolume`），
  且只在会话号仍是本实例这一条时才下发（会话号存在复用可能，宁可不动也不误伤其他通道）。
  补发发生在第一帧音频之前，连上的一瞬间也不会漏出一段声音。
  `SetMuted` 的返回值语义随之明确为「意图已被接受」，不再把「会话还没建立」当成「已生效」。

## v2.1.0 — 托盘常驻、收尾通知与发布链路（2026-10-21）

### Changed

- **画面上的双击不再切换全屏。** 之前 `RdpView` 把 `DoubleTapped` 直接接成「全屏 / 退出全屏」，
  代价是双击图标、双击选中文字这类日常操作在远端一律失效 —— 全屏变成误触。现在双击**原样转投远端**，

### Added

- **点关闭按钮先问一句：收进状态栏还是退出。** 之前点关闭就等于结束进程，挂机时必须小心翼翼

  - 「任务执行时隐藏到状态栏，空闲时退出」→ 按状态自动决定（`auto`）：跑着任务就只收进托盘，

  设置页「外观」新增「关闭按钮」四档下拉，随时能改回来（不然勾了「记住」就再也找不到入口）。

- **状态栏图标（自绘，无 WinForms 依赖）。** 自建一个从不显示的顶层窗口收回调，

  （`TaskbarCreated`），以及退出时 `NIM_DELETE` 干净摘掉，不留僵尸图标。

- **主控端单实例。** 窗口能收进托盘之后，用户很容易再双击一次 exe —— 之前会起第二个进程、
  第二个托盘图标、两套任务。现在用命名互斥体挡住，第二个进程只负责把已有窗口叫回前台然后自己退出
  （命名事件 + 后台线程通知，不对 WinUI 窗口做子类化）。

### Changed

- **「任务完成后自动退出」改走统一退出出口（`MainWindow.RequestExit`）。** 关闭拦截装上之后，
  原来那句 `App.MainWindow?.Close()` 会被自己的"关闭 Yomori？"弹窗拦住 —— 开了自动退出的用户
  每次都会看到莫名其妙的确认框，而窗口若收在托盘里，那个框根本看不见、程序反而退不掉。

- **安装包自己也要求管理员权限（双击即弹 UAC）。** 之前 `setup.exe` 外层清单是 Inno 默认的
  `asInvoker`，`PrivilegesRequired=admin` 只让它「启动之后再 runas 一次」——双击后先出安装向导、
  过一会儿才提权，跟主程序「双击立刻弹 UAC」不一致。现在 CI 先复制一份 Inno 编译器、把模板
  `SetupLdr.e32/e64` 的清单改成 `requireAdministrator`（`tools/patch_setup_manifest.py`），
  再用这套模板编译；`installer.iss` 相应加上 `DisablePrecompiledFileVerifications=setupldr`
  （Inno 6.7 起会校验模板哈希）。CI 里钉死 Inno Setup 6.7.3，编译完还会**读产物清单断言**
  它是 `requireAdministrator`，并挡住「只剩 950KB 引导器」的残缺产物。
  `PrivilegesRequiredOverridesAllowed` 已移除（`/LOWEST` 绕过提权那条路封掉）。

  > ⚠️ 别改成「编好的 setup.exe 事后打补丁」：它是「PE + 尾部追加的安装数据」，
  > `mt.exe` / `UpdateResource` 写回时会把追加数据整段丢掉（实测 75MB → 1,000,448 字节）。

- `installer.iss` 补上 UTF-8 BOM：没有 BOM 时 ISCC 按 ANSI 读，中文（快捷方式任务描述、
  `[Code]` 里的提示文案）会变成乱码。

- **通知改为只从主控端发。** 系统 Toast 只能在发出它的那个用户会话里显示，
  目标会话里弹的通知主控端用户根本看不到。所以代理侧（`RdpAgentRunner`）
  **已删除全部发通知的代码**；主控端下发的 `RdpCommand.NotifyOnTaskDone` /
  `NotifyOnAllDone` 现在**固定发 `false`**，只为让仍部署在目标账户里的**旧版代理**闭嘴。

### Fixed

- **安装完成后勾选「启动 Yomori」会弹「CreateProcess failed; code 740 请求的操作需要提升」，程序反而没起来。**
  根因在 Inno：带 `postinstall` 的 `[Run]` 条目**默认用 `runasoriginaluser`**（即 UAC 提权之前那个
  普通令牌），而主程序 `app.manifest` 是 `requireAdministrator` —— 拿普通令牌 `CreateProcess`
  必然被拒（740 = `ERROR_ELEVATION_REQUIRED`）。安装日志里能直接看到 `Run as: Original user`
  紧跟 `code 740`。现在该条目加上 `runascurrentuser`（继承 Setup 自己的管理员令牌），必定能起来。

- **完成通知从来没弹出来过 —— 根因是通知 API 在提权进程里静默失效。** 原实现用 Windows App SDK 的
  `AppNotificationManager.Default.Register()`。本机实测（2026-10-11）：非提权进程一切正常；但本程序
  `app.manifest` 声明 `requireAdministrator`，**提权进程里 Register/Show 都不抛异常，注册表键 /
  通知库 handler / 通知记录却一个都不产生** —— 通知从未投递；而"不抛异常"让原有的 catch 降级路径
  永远走不到，于是失败完全无声。现已改用**经典 Toast API**
  （`Windows.UI.Notifications.ToastNotificationManager`），提权与非提权实测都能正常投递；
  并在 HKCU 注册本程序的 AUMID 与显示名（Toast 头部显示"Yomori"）。同时补上状态自述：
  启动时把"通知已就绪 / 不可用 + 原因 + HResult"写进运行日志与 crash.log；`Show()` 的返回值也改为
  如实反映是否真的投出去了（旧实现排队后先返回 true，会把失败当成功）。

- **「检查更新」绝不把「查不到」说成「已是最新」**：网络失败、GitHub 限流（匿名每小时 60 次）、
  返回体解析失败、该渠道没有可识别的版本号，全部如实报成对应的失败 / 无发布状态，并写进运行日志；
  一份正式版都没发过时 `/releases/latest` 的 404 被当成正常状态（「该渠道暂无发布」）而不是错误。

- **本机自编译的包不再被判成「比远端新」**：版本号带 `-dev.local` 的开发版和发布版本来就不该放一起比，
  现在单列一个状态，明确说明这是自编译版并报出远端版本号。

## v2.0 — 多会话通道（2026-09-27）

远程会话从「单通道 + 系统 `mstsc` 窗口」重构为**多条会话通道并行执行 + 原生内嵌画面**。

### Added

**会话通道**

- **通道模型**：一条通道 = 目标主机 + 目标账户 + 凭据 + 指令桥目录 + 画面实例 + 运行状态。
  通道管理页支持新建 / 复制 / 删除 / 改名，以及逐通道的预检。
- **任务分配**：任务的 `channel_id` 决定它走哪条通道；下拉里「本地执行（当前会话）」是显式第一项，

- **启动计划**：`RdpChannelPlanner.Plan()` 分组 + 并发上限截断 + 跳过原因（纯函数，可单测）。
  指向不存在 / 已停用 / 没配账户的通道时**不执行**并说明原因，绝不静默改跑本地。
- **指令桥多实例化**：`RdpBridge` 从静态类改为实例类，按通道各持一份
  `command.json` / `status.json` / `stop.json`。
- **桥目录按账户名隔离**：`<ProgramData>\Yomori\rdp\<账户名>\`（见「升级注意」）。

  跑远程 / 并行任务时永远显示「空闲 / 00:00 / - / 0 / 0」—— 现统一走整轮口径的计算属性。
- **部署代理失败被误报成"需要管理员权限"**：真因是副本文件被常驻代理持有。
  现在按三档策略处理（原地覆盖 / 送走空闲旧代理 / 退到备用目录 `agent_b`），并给出准确归因。
- **画面被压成一条横带**：事件卡原先写死高度 —— 改为画面优先布局 + 事件卡可折叠。
- **通道页没有全屏入口**：全屏编排原先留在管理页 —— 抽成共用类后两页都能进，
  并加了"同时只允许一个全屏窗口"的守卫。
- **多账户并行时任务"跑完却被判异常"**：所有账户共用一份代理副本，日志与耗时统计都落在副本目录下，
  而 `ProgramData` 默认 ACL 只给 Users「读 + 建新文件」、文件归创建者所有 —— 一个账户建的
  `last_abnormal_report.json` / `runtime_history.json` / 同秒撞名的 `session_<时间戳>.json`，
  别的账户改不动，写统计直接抛异常并把整轮任务连坐判成异常。
  现在：**代理数据目录按账户分家**（`logs/<账户名>`、`runtime_stats/<账户名>`）、
  部署时给这两个目录放开 `BUILTIN\Users` 完全控制，且**统计写入失败只记日志、不再影响任务结果**。
- **「启动失败或提前退出」误判**：程序提权重启（典型是 BetterGI 未以管理员运行时用 `runas` 重启自己，
  原进程以退出码 553 秒退）或单实例转发，都会让直接进程立刻退出、由新进程接手。
  启动确认现在会开一个 10 秒**接力窗口**：监控目标出现或同名新进程在跑即判启动成功。
- **远程通道「停止执行」点了没用**（真机复现，见下方"停止链路"整段）：停止请求只在
  任务主循环的每秒计时回调里被检查，而收尾清理又同步堵在这个回调里 ——
  于是"点停止 → 界面卡住 → 代理那边迟迟不停"。现在停止检查独立成 500ms 并行循环，
  清理不再阻塞回传，主控端还会确认回执并自动补发。
- **设置页切主题 →「知道了」点不动、过一会儿整窗闪退**（真机复现）：`SelectionChanged` 里直接弹
  `ContentDialog`，而"改主题"会让 ComboBox 重新模板化并**二次触发** `SelectionChanged` ——
  同一个交互里连着两次 `ShowAsync`，第二次必抛 COMException `0x80000019`
  （*Only a single ContentDialog can be open at any time*）。异常落在 `_ = ...` 的
  fire-and-forget 调用里没人接，就成了未观察异常。现在三层收口：
  ① **所有** `ContentDialog` 一律走 `DialogHelper.ShowAsync()`（全局排队 + 异常就地落盘不抛）；
  ② 主题切换的反馈改成页面内一行文字（4 秒自动收起），不再弹模态框；
  ③ 对"值没变"的二次触发做幂等短路，不重复落盘、不重复提示。
- **「部署会话代理」点了像没反应，成没成只能猜**：成功分支原先只往运行日志追一行、改一个
  **通道页上根本不显示**的 `RdpStatusText` —— 而失败反而是弹窗的，一静一响正好把
  "部署好了"和"没点上"混成同一个体感（真机：22:24 那次其实成功了，日志里写着
  「已部署到所有用户共享启动目录…；已结束 1 个正在运行的旧会话代理」，用户只能来问）。
  现在成功也弹一次结果窗并说清后续动作，「移除代理」同样给回执；
  通道页在「开启远程桌面 / 部署 / 移除 / 重新检查」四个按钮下面补一行操作状态。
  另外判"要注销重连"不再只认「注销」二字 —— 日志里那句是「已结束 N 个…旧会话代理」，
  同样意味着新副本要等目标账户下次登录才启动。

### 停止链路（2026-09-27 二次修复）

真机复现记录：`rdp\zdh\status.json` 在点下「停止执行」后停在 `Phase=running` 再没更新，
日志停在「收到停止请求，正在收尾。」；`rdp\bh3\stop.json` 则从 12:26 一直躺到 15:00 没人消费。
据此定位到四个独立缺陷，一并修掉：

- **代理侧停止检查的位置错了**：原先挂在 `ScriptRunner` 的每秒计时回调上，而那个回调只在
  任务主循环里触发 —— 执行流程停在启动确认、接力确认、并发组等待、或正在做进程清理时，
  停止请求根本没人读。现在由一条与任务执行**并行**的 500ms 监听循环负责（`StartStopWatcher`），
  任何阶段都能在半秒内响应。
- **`ScriptRunner.RequestStop` 同步干重活**：整轮关键词清理要枚举全部进程并逐个 `taskkill`，
  实测十几秒（`bh3` 从停止到收尾隔了 14 秒），期间工作线程被占死，进度与心跳全部停摆 ——
  这就是"点了停止，界面像卡住"。现在请求只置标志位 + 立刻结束已登记的直接脚本进程，
  按关键词的统一三层清理改由 `RunCore` 的收口处 `CleanupForStop()` 执行。
  ⚠️ 这一步**不能只依赖任务主循环**：`ConfirmLaunchSuccess` / `TryConfirmRelayLaunch`
  一看到停止请求就返回 false，而那条分支原本只 `UntrackProcess` 不做任何清理 ——
  目标进程（含提权 / 单实例接力起来的新实例）会活下来，表现成"点了停止，游戏还在跑"。
  所以现在：那条分支在停止时**不解除登记**、也不记"启动失败"异常，直接把登记信息交给
  `RunCore` 收口处的统一收尾；清理范围按**已登记过的任务**（`_tasksByPid`）定，
  只覆盖真的启动过的那批，免得顺手杀掉只是关键词撞上的无关程序；紧急停止才扩大到全部任务配置。
  收尾必须在 `_currentProcesses.Clear()` **之前**跑，否则拿不到登记进程。
- **停止请求只发一次、发了不管**：代理漏读或版本过旧时，用户永远等不到任何反馈。
  现在主控端每 5 秒确认一次回执（代理把相位切成 `stopping` 或回"收到停止请求"的日志），
  没回执就补发（最多 5 次），到上限直接点名"目标代理多半是旧版本，请重新部署会话代理"。
  界面文案也固定成「已请求停止，等待目标会话确认…」，不再被代理回传的"运行中"盖回去。
- **`stop.json` 会残留**：执行期才检查停止，导致"点停止 → 又点紧急停止"时后一份永远没人收。
  现在代理收尾后清一次、空闲心跳分支顺手清一次、**主控端下发新指令时也清一次**。
- **关键词带 `.exe` 时清不掉游戏本体**：游戏的真实镜像名是英文（原神 = `YuanShen`、
  崩铁 = `StarRail`），按名字 `taskkill /IM "原神"` 注定打不中 —— **只剩"按窗口标题兜底"
  这一条路**能把游戏清掉，而窗口标题又不会带 `.exe`。原来拿原始关键词去比标题
  （「原神.exe」vs「原神」），这条路整个失效，表现成"停止了但游戏还在跑"。
  现在统一走 `ProcessHelper.TitleMatchKey()`：剥扩展名 + 大小写归一后再比标题与镜像名，
  `TerminateProcessesByWindowKeyword` 也带回退。
- **"结束了没有"完全看不出来**（真机再次踩到）：`taskkill` 的输出与退出码全被丢弃、
  异常也被吞，日志里只有"正在结束 X" —— 成功与失败长得一模一样。
  用户对着还在跑的游戏只能猜是"没杀掉"还是"画面没刷新"。现在：
  - `ProcessHelper.RunHidden` 把退出码与 stderr 带回来，`TerminateProcessName` /
    `TerminatePidTree` / 新增的 `TerminateProcessTree` 都返回 `ProcessTerminateResult`，
    失败会把 taskkill 的原始原因写进日志（顺带修掉"重定向了输出却不读"的死锁写法）；
  - 强杀被拒时**降级**：先换托管 API（异常信息比 taskkill 有信息量），
    再退到给目标窗口发 `WM_CLOSE`（应用层消息，反作弊驱动不拦，走游戏自己的退出流程）；
  - 清理末尾新增**复查**（`ReportCleanupResult`）：明确写"✓ 已复查确认任务相关的进程都已结束"
    或"⚠ 复查发现 N 项仍在运行：…"并给出下一步。
- **配置里写的是中文窗口标题，实际进程名是英文**：只按配置查，会同时踩"杀不掉"和
  "复查不出"两个坑。现在监控命中的那一刻会把该窗口所属进程的**真实镜像名**记下来
  （`LearnMonitorImageNames`），停止时按它清理与复查，不再依赖窗口是否存在。

> 升级提醒：这一版**必须重新部署会话代理**（代理代码变了），否则目标会话里跑的还是旧副本，
> 停止请求依旧不会被完整响应。

### 停止整棵进程树（2026-09-27 三次修复）

真机现象：**明明点了停止、任务也确实结束了，过一会目标会话又自己跑起来**。

复现记录（`bh3` 通道）：22:41:40 发出停止请求，22:41:47 结束掉脚本进程，22:42:01 日志打出
「✓ 已复查确认，任务相关的进程都已结束」；然而 22:42:57 目标会话里游戏被**重新启动**，
一路跑到 22:49:31 才收尾。事后查进程表，`March7th Assistant.exe`（PID 101176，父 PID = 被结束的
`March7th Launcher.exe`）**一直活着** —— 它才是真正干活的引擎，游戏正是它重新拉起来的。

根因有两层，缺一不可：

- **结束整棵树时把托管 API 的返回值当成了结论。** 任务配的 `March7th Launcher.exe` 只是个壳，
  真正干活的是它派生的 `March7th Assistant.exe`。停止时 `taskkill /IM /T /F` 被拒（拒绝访问），
  降级到 `Process.GetProcessById(pid).Kill(entireProcessTree: true)` —— 它**回报"结束成功"，
  却只带走了根 PID**；子进程发现游戏窗口没了，就自己 `游戏终止 → 游戏启动` 把游戏拉回来。
  现在 `ProcessHelper.TerminateProcessTree()` 改成五步，**任何结束动作之后都必须自己复查**：
  - **动手前**先用一次 Toolhelp32 快照（`NativeMethods` 新增 `CreateToolhelp32Snapshot` /
    `Process32FirstW` / `Process32NextW`）把整棵树记下来 —— 根进程一死，进程表里就只剩孤儿记录，
    那时再想按 PPID 补课已经晚了（这正是当初漏网的直接原因）。父子关系自己拿，
    也不受会话限制，能列到目标会话里的进程；
  - `taskkill` 先试一把；
  - **复查①**：不看退出码，只问"这些 PID 还在不在"；
  - 剩下的自己动手，**倒序遍历 = 从叶子往根**（先断掉会自己重启的引擎，最后才收壳）；
  - **复查②** 才给结论，失败就把「整树 N 个进程中仍有 M 个在运行：…」写进日志。
  `IsSameProcessAlive()` 还会比对镜像名，**防止 PID 被系统复用**后把无关的新进程误判成残留。
- **清理与复查用的名字不是同一套，复查因此打出了假的 ✓。** `BuildCleanupPlan` 只收
  `script_path` 的文件名和 `wait_process_name` —— 活下来的那个 `March7th Assistant.exe`
  **既不是脚本文件名、也不在 `wait_process_name` 里**，于是清理和复查两边都看不见它。
  现在：
  - **任务名**（经 `ProcessHelper.LooksLikeImageName()` 把关，避免把「原神日常」这类显示名
    当成进程名）纳入「启动脚本进程」阶段，清理与复查共用同一份计划；
  - 脚本进程**实际派生的后代**由 `ScriptRunner.LearnScriptDescendants()` 登记，
    `TerminateScriptDescendants()` 结束，`ReportCleanupResult` 按同一份名单复查。
    记的是 **PID 而不是名字** —— 脚本常会派生 `conhost.exe` 这类公共进程，
    按名字清会误伤系统里别的同名实例；
  - 学习时机放在**停止链路上最早的一刻**（`TerminateTrackedProcesses`，代价只是一次毫秒级快照）
    以及 `CleanupProcessesForTasks` 开头，并且**紧接着登记就收后代** —— 不给它
    "把游戏重新拉起来"的时间窗；
  - 复查若发现漏网的是**脚本自己的子进程**，会单独点名并提示它可能重新拉起游戏，
    不再和"游戏杀不掉"混在一句话里。

顺带修到的一处：`ProcessNamesForTask` 现在也包含任务名，于是「启动确认」阶段
"直接进程秒退 / 单实例转发"的**接力判定**能认出由启动器派生的引擎进程 ——
像 `March7th Launcher.exe` 这种"起完就退"的壳，以前会被误判成"启动失败或提前退出"。

升级提醒同上：这一版同样**必须重新部署会话代理 + 注销目标账户重连**。

### 耗时统计（2026-09-28 修复）

真机现象：**「耗时统计」页永远空的**，跑多少轮都不出现一行。

根因不是界面坏了，而是**数据根本没主控端在读**：

- 任务启用后基本都交给了会话通道，代理在**目标账户**里执行；
- 代理的统计写在**它自己那份副本**的 `runtime_stats\<账户>\` 下
  （v2.0 为了绕开多账户互相锁文件才这么分家的），跟主控端那份 `runtime_stats\` 不是一个目录；
- 主控端这一页只读自己那份 —— 那份从来没人写。远程主机的通道更是连对方 ProgramData
  都读不到，所以光"让主控端去翻副本目录"也修不干净。

修法分三层（协议 / 汇总 / 兜底）：

- **`RdpBridge` 新增第四种桥文件 `stats.json`**：代理每跑完一轮，把**合并后的全量历史**
  发布到自己的桥目录（`RdpAgentRunner.PublishStatsSnapshot()`）。写在 `ScriptRunner`
  写完统计之后、**会话收尾之前** —— 收尾方式若是注销，代理会被一起带走，晚一步就没机会写了。
  代理启动时也先补发一次，免得刚重启时页面还是空的、被当成故障。
  发布的是全量历史而不是本次会话，多次写入天然幂等。
- **主控端汇总**：`StatsSourcePlanner` 列出所有来源（本机 + 各启用通道的桥），
  `MainViewModel.RefreshStats()` 合并成一张表，**新增「来源」列**标注每行来自哪条通道。
  同一个脚本在不同账户跑过就是多行，便于横向比耗时、给超时定值。
- **老代理兜底**：还没有发布逻辑的代理（或刚升级、代理还没重新部署）走
  `runtime_stats\<账户>\runtime_history.json` 兜底读取，仅对**本机**目标生效；
  通道的 `bridge_path` 指向远程共享目录时不做这一步。
  同一通道两路都有数据时**只认桥里那份** —— 快照本来就是从副本那份算出来的，合并会把次数翻倍。
- 统计页补了**空状态说明**（讲清数据从哪来、刚升级要重新部署代理）与「打开桥目录」按钮。

### 会话通道菜单（2026-09-28 修复）

真机现象：点「**会话通道**」父项打开的是多画面页，点子项「**多画面（全部通道）**」也是同一个页面 ——
两个入口长得一样，看着像功能重复。

- **父项只负责展开/收起**：点它不再打开任何页面，多画面入口唯一落在子项上。
  老 tag `channels`（通道管理页「打开多画面」还在用）内部统一映射到子项的 `multiview`，
  跳转结果不变、菜单选中态也落在子项上。
- **点第二下能收起来了**：原先父项点击被无条件置成展开，收不起来；
  现在按"点击前后状态"判定切换，不受 NavigationView 内部是否自己切换的影响。
- **展开有级联动画**：子项淡入 + 从上方轻微下滑（单项 180ms、逐项错开 25ms、总延迟封顶 120ms），
  通道多也不拖沓。只在**点父项展开**时播 —— 子菜单因会话变化重建（跑任务时很频繁）不播，否则菜单一直闪。

### Upgrade notes

⚠️ **桥目录规则变更，升级后必须重新部署会话代理**

```text
旧：<ProgramData>\Yomori\rdp\
新：<ProgramData>\Yomori\rdp\<账户名>\
```

已部署过代理的机器，升级后**重新点一次「部署会话代理」**，然后**注销目标账户再重连**
（代理是账户登录时由启动项拉起的）。否则表现是"代理明明在跑，却一直显示不在线"。

其他：

- 旧配置自动迁移出一个默认通道并让任务指向它，**原来能跑的行为不变**；
- 代理部署成功后旧代理已被结束，同样需要注销目标账户再重连；
- 耗时统计要多看到通道那一份，同样得重新部署代理（新代理才会发布 `stats.json` 快照）；
  没重新部署也不至于空白 —— 本机目标的通道会走副本目录兜底，只是数据要等代理下次落盘才更新；
- 内嵌画面改用原生 FreeRDP，旧配置里的 `rdp.embed_remote_desktop` 键仅为兼容保留，读进来恒为 `false`。

### Known limitations

- 一次最多 8 条通道并行；多画面每页最多 4 格（8 路同时渲染开销不可接受）。
- 弹出到独立窗口的画面，只能从主窗口菜单「执行中的通道」再进页面找回来。
- 心跳宽限期上限 90 秒，因此 90 秒内的真断线最迟约 90 秒才告警（刻意折中）。
- 内嵌会话暂不支持剪贴板互通。
- 桥的 `command.json` / `status.json` / `stats.json` 仍是 PascalCase，与 `config.json` 的 snake_case 约定不一致。
