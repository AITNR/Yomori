# Yomori 全面性能优化计划书

日期：2026-10-31。审计基准：`05332f6`。状态：计划阶段，尚未实施。

## 1. 目标与范围

降低主控与常驻代理在空闲、任务执行、日志高吞吐和多路 RDP 下的 CPU、Private Bytes、分配率及文件 I/O；改善启动、切页、配置编辑和停止响应。

采用“建立基线 → 按收益与风险分批实施 → 同场景对比 → 保留回退”的流程。默认保留分辨率、画质、帧率上限、音频、输入、任务顺序、WaitFirst、停止及日志完整性。节能模式若需要降低刷新率，应作为显式可选策略独立评审。

本次仅新增本计划书；未修改生产代码、配置或安装目录，未启动 GUI、重连会话或执行构建。文件阅读由三个 deepseek-v4.1-flash 子代理分别覆盖渲染、后台执行、UI；主代理核对关键实现与日志后汇总。工作区原有两个未跟踪文件保持不动。

## 2. 现状及证据边界

### 2.1 已完成的优化，不重复立项

- 独立 `Yomori.Agent` 工程避开 WinUI/WindowsAppSDK 初始化。
- runner 最多 16 个活动 worker；延迟与日志轮询使用可取消等待。
- 日志、事件、待处理字节和单拍读取均已有边界；会话与渲染资源已有释放路径。
- native/managed 帧缓存按尺寸复用；软位图复用，每拍仅一次抓帧。
- RDP 依据帧序号合并更新，无新帧不 Present；多画面翻页已有解挂逻辑。
- 自动保存已有 600ms 去抖、原子替换与重入防护；代理空闲心跳已有 5 秒节拍。
- AVC420/444、DXVA2、能力协商诊断与软件恢复已实现。

### 2.2 当前可以确认什么

最新本地日志 `logs/2026-10-31(3).log:175,179` 显示实际 codec 15、decoder=dxva2、hwactive=1，hw_frames 随时间增长。这支持该次真实会话已使用硬解。较早文档里“真实会话尚未验证”的状态已被这份新日志推进，但还不能推断所有目标机器都成功或已有确定 CPU 降幅。

同一日志 `:158` 记录双路时 private=971 MiB、working_set=793 MiB、managed=20 MiB、151 线程、2180 句柄、2 个 client/renderer，任务和日志 worker 均为 0。这是已有日志快照，不是本次重测，也不能证明泄漏；其中 native、解码表面池、驱动和 XAML 的占比尚未拆解。

本次进程查询仅发现独立代理，未发现名为 Yomori 的主控。代理瞬时约 38.3 MiB Working Set、10.0 MiB Private；累计 CPU 时间不能当 CPU 使用率。未执行真实双路基准。

10 月 17 日的约 639 MB 双路数据以及更早 1.9 GiB 数据都不能直接作为当前硬解版本基线；旧审计中“无泄漏”“托管优化没有收益”等判断也只适用于其当时的采样条件。

### 2.3 计量原则

- CPU 同时报进程 CPU 时间增量与按逻辑 CPU 数归一化的使用率，并统计 PowerShell/CIM 等辅助进程成本。
- Private Bytes、Working Set、GPU local/non-local 分列，不简单相加；提交量不等于物理驻留量。
- QPC 阶段耗时是墙钟时间，可能包含等待；嵌套的解码、合成、复制计时不能相加冒充 CPU 时间。
- 除字节数等可推导的局部成本外，本文不给未经测量的整体百分比承诺。

## 3. 优先级与实施顺序

P0 表示首批建立证据或处理明确高频成本；P1 为随后实施的局部优化；P2 为依赖采样的结构性实验。优先级不代表已测得的热点排名。

|---|---|---|---|---|
| A0 | 基线、CPU 栈及 native/GPU 内存归因 | 避免错误优化，明确瓶颈 | 低 | P0，先做 |
| A1 | 进程/窗口/命令行共享采样 | 减少 PowerShell、CIM 与系统枚举 | 中 | P0，首批 |
| A2 | 可见性和新帧驱动渲染调度 | 降低空闲与隐藏窗口唤醒 | 中 | P1，首批 |

## 4. 具体方案

### A0. 建立可重复的当前版本基线

复用 `winui3/tools/profile_rdp_cpu.ps1`、`watch_memory.ps1` 和每分钟 memory、每 5 秒阶段日志。CPU 脚本目前只接收 Yomori 主控，需要另行扩展多进程聚合或配合 ETW；内存脚本主要选单个进程，不能直接代替所有代理的合计。

记录 commit、EXE/DLL 哈希、加载模块路径、系统/驱动、CPU 核数、显示缩放、codec、分辨率和每路输出 FPS，确保安装版与源码版不会混比。

先做 0/1/2 路，资源允许时再做 4/8 路。分别测试静止桌面、局部滚动、同一段全屏动态内容；预热 2 分钟，采样至少 5 分钟、重复 3 次。长期稳定性另跑 1–2 小时。采集 CPU、分配率、GC/LOH、Private/WS、GPU 内存、线程、句柄、文件打开/写入、FPS 和输入延迟。优先用 CPU 栈确认 memcpy、色彩转换、解码、Present 等实际成本。

native 内存归因至少区分 decoder surface pool、GDI surface/cache、桥帧缓存、staging/backbuffer 和驱动分配；只有托管堆小，不能推出所有 C# 侧 CPU 优化无效。

### A1. 合并进程监控与后代扫描

证据：`ScriptRunner.cs:1321` 在任务轮询中调用监控判断，`:1422` 等待 250ms；`ProcessHelper.cs:422-458` 的命令行判断每次启动 PowerShell 并通过 CIM 枚举系统进程。`ReadToEnd` 位于 `WaitForExit(8000)` 前，现有 8 秒并不覆盖整个阻塞读取，实施时一并核查取消和超时。仅启用相关监控模式时触发此成本，不能推广到所有任务。

方案：

1. 每个 runner 设置单一采样协调器，按 PID、会话、进程名、窗口和命令行提供不可变快照，多个任务复用。
2. 普通进程/窗口采样保持原有检测需求；命令行使用可取消的常驻查询或候选 PID 查询，避免每轮启动 shell。先验证权限和兼容性，再决定是否保留 CIM 兜底；不默认引入复杂 PEB 读取。
3. 进程退出/新建提示可作为唤醒信号，仍保留周期校验。无法读取与确认“不存在”应分开，避免误判任务完成。
4. `ScriptRunner.cs:1681-1768`、`ProcessHelper.cs:121-217` 的后代发现复用一次 Toolhelp 快照，预建 parentPid→children 索引，减少多个 worker 和 BFS 节点重复扫描。
5. 对 `Process.GetProcesses*` 返回的全部对象明确 Dispose，包括提前 return 分支；跨采样缓存身份应处理 PID 复用。

验收：1/4/16 并发下统计 PowerShell 启动数、CIM 调用数、CPU 和句柄；覆盖拒绝访问、启动器先退、孙进程迟到、停止和任务归属。首版保持现有检测语义与最大延迟；若采用 1 秒采样，必须单独评审延迟变化。

### A2. 渲染计时器按窗口可见性和新帧调度

证据：`Views/RdpView.xaml.cs:487-501` 使用 16ms 周期 timer，`:762-784` 已检查 suspend、IsLoaded 和帧序号，但这些条件不能完整表达窗口最小化、隐藏及所属弹出窗口可见性。

方案：最小化/隐藏且无其他可见消费者时停止抓帧与 Present，网络和任务继续运行。FrameArrived 只合并标记并请求一次 UI 调度，限制最多一个待执行渲染任务；连续动态画面保留现有最高节拍。恢复时强制补首帧，原生线程不直接操作 XAML/D3D。侧栏每秒刷新和通知动画也按其可见性暂停，先确认调用链，避免暂停承担业务职责的计时器。

验收：隐藏 60 秒抓帧/Present 为零；恢复后不黑屏，目标两次呈现机会内出图。覆盖托盘、最小化、弹出、全屏、不同窗口接管和断连恢复。该项主要降低 UI 唤醒，不等于远端编码或解码停止。

### A3. 分离日志发现与日志消费

证据：`ExternalLogTail.cs:187-297,333-356` 每拍候选枚举、排序、检查与重新打开；`ScriptRunner.cs:241-312` 为每个任务启动独立轮询。已有递归深度、文件数、字节和行数上限。

方案：缓存候选集与当前活跃文件；用 watcher 辅助发现新建、轮转、截断，定期全量重扫兜底。普通追加只做必要的长度/游标检查；按共享目录合并发现扫描，保留每个任务独立读取与过滤语义。复用受限读缓冲；空闲退避不得影响停止或最终日志收尾。

验收：复用 LogChecks，补充 watcher 丢事件/溢出、共享目录断开、跨日轮转、编码跨块和大量历史文件；比较目录枚举次数、打开次数、分配率。日志无漏行、无重复、有序续读。

### B1. 减少一层全帧复制

证据：`RdpEmbeddedClient.cs:306-345` 将 native frame 复制到托管数组；`RdpD3DRenderer.cs:283-310` 随后 Map staging 并再次复制。

方案：新增版本化 native 接口，直接写入已映射的 staging 指针，显式传入目标容量、row pitch 和预期尺寸/帧代次。维持当前 UI 线程上的 Map/Unmap/Present，native 锁仅保护帧读取；Map、Present 和异步等待不得在全局锁内执行。尺寸不匹配返回重试，所有异常路径保证 Unmap。SoftwareBitmap 路径保留已有托管快照，D3D 失败仍可安全回退。

局部理论收益：1080p BGRA 一帧约 7.91 MiB；若不再分配 D3D 路径的托管快照，可少约一帧数组/路，并少一次同尺寸 memcpy。30 FPS 单路对应约 237 MiB/s 的一次复制负载；这是数据量估算，不是 CPU 或总内存降幅保证。

验收：对比原始像素；覆盖奇数宽度/非紧密 pitch、1080p/4K、尺寸突变、连接取消、并发断连和 D3D 回退，跑 DecodeChecks 与 native 生命周期测试。

### B2. dirty region 局部更新

证据：`Yomori.RdpNative/ycn_rdp.c:611-640` 在 EndPaint 全帧 memcpy；后续托管与 staging 也是全帧。局部变化仍支付整帧成本。

方案：先让各 codec/GDI 路径产生可验证的 dirty region 元数据，合并跨多次未呈现更新；缺少可靠区域、首次帧、尺寸变化、恢复或区域过碎时回退全帧。逐步实施 native frame 局部更新、局部上传，不一次替换整条管线。

双缓冲翻转不能直接假设每张 backbuffer 已含前帧；必须保持 canonical 图像或显式同步各 backbuffer。canonical texture 可能增加约一帧显存，应实测带宽收益与内存代价。AVC444 辅助流、surface 映射、重叠区域和光标合成必须纳入有效区域。

验收：用相同录制输入对比全帧基准；局部滚动/时钟/光标与全屏动画都无残影，复制字节随有效变化面积下降。无收益或内存代价过高时保留全帧路径。

### B3. 合并状态写盘并减少重复 ACL 操作

证据：`RdpBridge.cs:354-387` 每次读改写状态；`:737-767,833-855` 会对目标、临时和替换后文件设置权限。`RdpAgentRunner.cs:174-220` 的运行状态更新比空闲心跳更频繁。

方案：先去除可证明重复的 ACL 操作，再优化状态写入。依赖目录继承和文件身份检测缓存结果，保留跨账户失败后的修复；不能简单删除所有权限设置。将计时字段和非关键状态合并写入，finished、task_done、停止回执等关键事件立即刷盘，心跳继续满足 20 秒超时约束。

进阶内存权威状态必须先明确 Agent、主控 ResetStatus 和其他 writer 的所有权；通过 commandId/epoch/version 避免缓存覆盖外部重置，再考虑不读回自己的完整 JSON。维持旧代理和共享目录协议兼容，不直接切换到仅本机适用的命名管道。

验收：统计反序列化、写字节、文件替换与 ACL 次数；验证跨账户、断网重试、旧代理、reset、异常退出和 finished 恰好一次。不能将过期内存状态写回新命令。

### B4. 文件日志批写与日志 UI 批处理

证据：`FileLogger.cs:42-50`、`ExternalLogStore.cs:249-260` 逐行追加；`MainViewModel.cs:2567-2587` 在上限后头部删除。现有实时日志已经批量传输，普通日志 ListView 已存在，不能把建议写成“首次加虚拟化”。

方案：按目标文件使用有界单 writer，复用流和 UTF-8 编码器，按字节数/行数/短时间窗口 flush。必须明确队列满时的背压与计数；归档不可静默丢行，普通诊断允许降采样时需显式标记。错误与退出优先刷新，轮转和权限修复保持闭环。

UI 将多行合并为一次 dispatcher 工作，滚动至底部最多每批一次；历史缓存可改环形结构，但仅在测得头删/通知开销后实施。可见列表保持可虚拟化，筛选结果采用增量或批次更新。不要为每行创建 Task。

验收：100/1000 行每秒回放下记录 UI 帧耗时、分配率和文件打开数；正常退出完整落盘，强杀损失窗口明确且有界；已有 4000 行等边界继续生效。

### C1. 自动保存与启动文件工作分离

证据：`MainViewModel.cs:1069-1098` 在 UI 线程规整任务、应用开机项、序列化并保存；`ConfigManager.cs:76-106` 做 sanitize、序列化和文件写入。`Initialize():806-831` 同步清理外部日志、加载统计；更新包清理和更新检查已经在后台/延迟执行。

方案：首步使开机项仅在值或启动路径变化时应用，跳过无变化的序列化结果写盘。再在 UI 线程捕获稳定快照，将文件写入交给单一有界后台 writer；所有入口按修订号排序，旧快照不可覆盖新值，退出需等待最新修订保存。不能直接把可变 Config 交给 Task.Run，也不能沿用“落盘期间吞全部通知”的同步假设；新改动需保留为 dirty。保持秘密字段清理和原子替换。

将启动期目录清理移到首屏之后；统计页按需异步加载，区分读取失败与空数据，避免临时失败覆盖有效缓存。Banner、mascot 等图像已有解码尺寸限制，先测缓存命中与峰值，不盲目增加图片常驻缓存。

验收：大量任务编辑、OneDrive 慢盘、权限失败、连续编辑后立即退出、导入和开始任务前的配置一致性。记录冷/热启动首屏时间、保存次数和 UI 卡顿。

### C2. native、解码表面和 D3D 固定开销实验

仅在 A0 归因后实施。优先检查 codec/context 是否按需分配、DXVA2 surface 数量与参考帧要求、尺寸切换是否保留旧池、缓存上限是否符合实际会话需求。不要凭总 Private 差值把剩余内存都归为 FreeRDP。

每个 renderer 目前独立创建 D3D device（`RdpD3DRenderer.cs:112-168`）。只有设备开销占比值得优化时，实验同一 UI 所属线程/适配器内的设备共享，交换链仍归各 panel。共享设备会扩大 DeviceLost 影响，不能跨 UI 线程随意复用 immediate context。纹理缓存必须有预算、过期与压力释放；增加缓存可能提高稳态内存，只能在切页延迟收益明确时采用。

GPU surface 直显/减少 GPU→CPU 回读属于后续架构实验，需处理 DXVA2 D3D9 与当前 D3D11 的互操作、AVC444 合成、图形层叠及软件回退，不纳入首批承诺。

验收：各自独立 A/B；多路、20 轮尺寸/全屏/页面切换和设备丢失恢复。Private/GPU/句柄达到平台期，资源计数回落，无串图或渲染死锁。

### C3. 构建与发布参数

确认 Release/x64 和实际加载 DLL 对齐。对 Agent 和主控分别比较默认 JIT 与 ReadyToRun 的冷启动、CPU 和 Private；代码体积增加与启动收益应一起记录。self-contained 主要影响分发和运行时依赖，包体缩小不能作为运行内存下降的证据。

不直接开启 WinUI 主程序 trimming/NativeAOT；XAML、反射和运行时依赖需要单独兼容性验证。GC 模式/堆上限仅在证据显示 GC 是瓶颈时做 A/B，不默认设置 Server GC 或强制频繁收集。

### C4. 其他 UI、图像和异常路径优化（按采样结果选做）

- **多画面布局**：`Views/RdpMultiViewPage.xaml.cs:136-180` 每秒先 Collapsed 所有格位再 Assign/Place/UpdateChrome，虽然 SetClient 对同一实例已有短路。建立通道顺序、页码与可见状态签名，布局仅在变化时执行，进度和 chrome 单独更新。用 1/4/8 通道比较 XAML 属性写入与 UI 耗时，覆盖分页、弹出、锁定、静音和失联，防止签名遗漏导致陈旧状态。
- **首页图片**：`Views/HomePage.xaml.cs:28-34,105-160` 允许最大 32 MiB 源文件、固定 2048 物理宽解码，每次导航重读。已有尺寸限制，仍可按实际控件尺寸/DPI 选择解码尺寸，并增加离页取消和请求世代检查；只有反复访问确有收益时采用容量很小的时间戳缓存。验证 4K/200% 缩放清晰度、快速切页、换图失效和峰值内存，不能为了缓存扩大长期驻留。
- **通知持久化**：`Services/NotificationCenter.cs:146-150,191-200,255-267` 在 UI 线程同步写入，集合已有 50 条上限。复用单一后台写入与修订号合并机制，未读数仍即时更新，正常退出 flush。测试高频新增/已读/删除、慢盘和重开一致性；保持实际启动清理策略，不假设历史一定跨启动保留。
- **超时截图峰值**：`Services/ScreenshotService.cs:18-35` 按整个虚拟桌面分配 bitmap 并压缩 PNG，多个 runner 超时可能重叠。首步用全进程有界并发控制与像素预算保护，记录截图排队和捕获时刻；截图失败或慢截图不能阻塞停止。缩小尺寸/改有损格式会影响诊断质量，列为可选设置，默认不变。测试双 4K/多通道同时超时，保持 before/after 对应正确且不会因排队在进程终止后才拍“before”。
- **退出清理**：`Views/MainWindow.xaml.cs:154-173,797-816` 的清理未覆盖所有铃铛计时器和匿名订阅；VM 的内存采样计时器也需纳入统一幂等关闭入口。窗口隐藏时停止装饰动画，正常关闭解绑具名处理器、取消在途加载、等待必要持久化。进程生命周期订阅本身不能证明泄漏，重点验证关闭期间不再回调已销毁 XAML。

以上属于 P1/P2 独立小批次：优先隐藏窗口和布局去重，图片缓存与异常路径只在场景命中时实施。不会把低频截图或每分钟采样默认判定为常态 CPU 主因。

## 5. 验证与验收门槛

| 维度 | 场景 | 判定 |
|---|---|---|
| 空闲 CPU | 主控首页、托盘、1/4 个空闲 Agent | 比较 3 次同场景 CPU 与唤醒；确认暂停的是渲染，不影响业务 |
| RDP | 1/2/4 路静态、局部、全屏动态 | 相同 codec/画面/分辨率/FPS；画质和输入保持，CPU 与复制量可归因 |
| 执行 | 1/4/16 任务与三种监控 | 等待、WaitFirst、停止、超时和清理语义不退化 |
| 日志 | 100/1000 行每秒、目录大、轮转 | 无漏重行；队列有界，结束后排空，CPU/分配/I/O 可比较 |
| UI | 4000 行、任务多、连续切页/全屏 | p95 UI 耗时不回退，计时器与订阅无单调累积 |
| 内存 | 预热后运行 1–2 小时，20 轮断连/重连 | 排除高水位后稳定；session/renderer/worker 成对回落，超阈值追查归因 |
| 持久化 | 快速编辑→退出、失败重试、重开 | 最后修订保存且重开一致，无旧快照覆盖和秘密字段泄露 |

建立基线后再冻结具体数值目标。建议验收策略：中高风险优化若目标场景 CPU 改善未超过运行间波动，或内存收益不能稳定复现，则不合入；可暂用至少 10% 的目标热点/阶段成本改善作为立项参考，不能当整体 CPU 保证。其他核心场景超过 5% 的可重复退化需解释或回退。不同内容/FPS 的样本不直接计算降幅。

复用测试：RunnerMemoryChecks、Yomori.LogChecks、DecodeChecks、native_memory_checks.py、native_decode_checks.py、AVC444/GFX 能力测试。只为变更补有意义的边界回归；真实 RDP、跨账户、音频/输入和长期资源曲线仍需端到端验收，不能由失败连接测试替代。

## 6. 分批交付与回退

1. 基线包：场景清单、哈希、CSV/ETL、实际 codec/FPS 和内存分解，确定首批热点。
2. 后台与空闲包：A1/A2/A3 分独立提交，每项附前后对比与回归。
3. 数据通路包：B1 先独立验收，再做 B2；B3/B4 单独交付，避免图形与协议风险混合。
4. 响应与内存包：C1 后执行，C2/C3 仅在收益证据充分时继续。

native ABI 变动需版本/结构大小校验，托管与 native 成套部署。高风险路径保留旧全帧/软件回退实现用于 A/B，回退不覆盖用户配置。每批输出独立构建目录与精确产物路径；计划阶段不发布、不部署、不提交代码。

暂不采用：EmptyWorkingSet、定期 GC.Collect、降低默认分辨率/音频/帧率、删除可靠性看门狗、把有界集合直接称为泄漏、单缓冲替换当前 flip swapchain、未经归因的大规模 UI 框架迁移。

## 7. 建议首先执行的范围

先批准 A0 与 A1/A2/A3 的小范围实现：可解释的重复查询和空闲开销最适合先减。第二批优先 B1；B2、共享设备和 GPU 直显需要更强的图像一致性与生命周期验证。最终目标以相同体验下的实测结果为准，不能预先承诺“CPU 降到某值”或“内存减半”。
